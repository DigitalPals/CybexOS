# ISO and installer audit — 2026-09-23

Audited checkout: `3c585cd`, followed by the local fixes described below.
Host: `zbook`, Fedora 44. This is a source/configuration audit with automated
tests, not validation of a newly built or booted ISO.

## Result and verification

The project has a complete VM-based ISO builder, offline application payload,
Hyprland/Quickshell live session, welcome application, and Anaconda Web UI.
The earlier full-application ISO passed offline UEFI installation and an
installed-disk boot; [VALIDATION.md](VALIDATION.md) identifies that exact
September 6 image. Those results do not qualify current source.

Checks performed in this audit:

- `./tests/run`: passed, including 895 JavaScript tests and repository source,
  integration, helper, and policy checks. The real-engine Quickshell lifecycle
  smoke test was explicitly skipped because a managed desktop was active.
- `image/tests`: all 11 existing tests passed; all 13 passed after adding the
  repository-policy regressions below. Qt welcome loading used an isolated
  PySide6 6.11.2 environment with `QT_QPA_PLATFORM=offscreen`, not the exact
  Fedora image package environment.
- Fedora 44 Kickstart parsing passed for the expanded compose configuration
  (139 native selections, before pinned application RPM additions, and three
  Flatpaks) and the interactive installation cleanup script.
- All six packaged Hyprland templates, three Distrobox launcher templates,
  and the Hermes service rendered with the packager's actual Jinja context.
- Static analysis passed again after the code changes; `git diff --check`
  passed.

An actual `image/build` invocation stopped at its prerequisite check because
this host lacks `cloud-localds`. No builder VM or disk was created. The
live-test harness also assumes `/usr/share/OVMF/OVMF_{CODE,VARS}_4M.fd`, which
this Fedora host does not provide; its firmware uses other paths/formats.
The local `/data/pxe/iso` tree and previous image-output directories are absent.
The hostname `thebeast` did not resolve; an SSH attempt at `10.10.0.7` stopped
at the unknown-host-key check. Existing PXE image contents were not inspected.

Fresh compose, live boot, encrypted installation, installed boot, physical
hardware, Secure Boot, and current iVentoy behavior remain unverified.

## Small fixes made during the audit

1. [applications](applications) requested `brave-origin.repo`, but the reviewed
   policy is `roles/apps/files/brave-browser.repo`. Python silently ignored
   the missing file, omitting the Brave repository while the package contract
   selected `brave-origin`. Corrected the filename and made missing policy
   files fail explicitly. Added tests for the actual Brave repository contract
   and missing-file behavior.
2. [Live image CI](../.github/workflows/live-image.yml) did not trigger on
   desktop, base-role, or helper/asset changes that affect the image. Expanded
   its path filters to cover these inputs and `VERSION`.

No installed desktop configuration was changed. No ISO was published, so no
iVentoy refresh was required. Temporary test dependencies and the task-created
Python bytecode were removed; no VM, disk, screenshot, or build log is retained.

## Proposed minimal installation

Omarchy v4.0.4's [shared setup form](https://github.com/omacom/omarchy/blob/v4.0.4/install/provisioning/setup-form.sh)
collects keyboard, account/password, optional Git identity, hostname, and
timezone. Its [ISO configurator](https://github.com/omacom/omarchy-iso/blob/7cfb7111a06873d61c45d37034577d4ba08d3f4f/configs/airootfs/root/configurator)
then asks about the disk and confirms changes, with encryption enabled by
default. The [installation implementation](https://github.com/omacom/omarchy-iso/blob/7cfb7111a06873d61c45d37034577d4ba08d3f4f/configs/airootfs/usr/share/omarchy-iso/orchestrator/phases_impl.py)
enables autologin on encrypted normal installations. The pinned ISO source
is the current development branch inspected during this audit; it may be
newer than the released ISO. Older Omarchy 3 manual limitations should not
be assumed to describe this source.

Recommended CybexOS flow:

| Screen | Required choices | Defaults / secondary choices |
| --- | --- | --- |
| Your setup | Username, password and confirmation, keyboard layout | Language, timezone, and hostname prefilled where possible, editable under More options; keyboard test field available. |
| Install location | Target disk, shown by model and capacity | Automatic LUKS2-encrypted Btrfs root/home; boot partitions managed by Anaconda; autologin enabled. Advanced storage remains available. |
| Review and install | Confirm the exact disk changes | Show encryption, account, keyboard, and erase summary, then installation progress and reboot. |

Collect the password once, use it for LUKS and the account, and leave root
locked. Keep the password out of persistent logs and generated artifacts;
use the installer's supported secret handling and store the account hash.
After reboot the intended flow is **Cybex disk-unlock prompt → desktop**.
Move optional Git identity and application choices into later personalization.
When encryption is disabled in Advanced, default back to a graphical login.

Keep Anaconda's storage backend and validation. Fedora 44's Web UI tag 68
supports branding, CSS, and hiding selected pages, but its
[customization documentation](https://github.com/rhinstaller/anaconda-webui/blob/68/docs/customization.rst)
says Web UI add-ons are not implemented. The existing
[encryption](https://github.com/rhinstaller/anaconda-webui/blob/68/src/components/storage/storage-configuration/DiskEncryption.jsx)
and [account](https://github.com/rhinstaller/anaconda-webui/blob/68/src/components/users/Accounts.jsx)
components use separate password state. Implementing a combined screen
requires a maintained Web UI change or a custom frontend using Anaconda's
interfaces. Begin with a small Web UI change and measure its maintenance cost.

Equal initial passwords do not automatically stay synchronized. Omarchy has a
[separate disk-password command](https://github.com/omacom/omarchy/blob/v4.0.4/bin/omarchy-drive-password).
A later CybexOS password-settings screen should coordinate both changes or
clearly identify which password it changes. Also test GNOME Keyring access
under autologin: disk unlock alone does not establish the normal login PAM
password handoff, so applications may otherwise prompt again.

## Prioritized improvements

1. **Make one shared desktop/image contract.** Package the same wallpaper,
   appearance defaults, helpers, system policies, and boot theme from both
   install paths. Keep personal plugins and machine-specific overrides out
   of that contract. Add fresh-account parity assertions.
2. **Complete the branded boot path.** Reuse the current Cybex artwork and
   colors for a short boot menu, Plymouth animation and encryption entry,
   welcome screen, and installer. Keep readable error output and a recovery
   menu. A consistent restrained animation will contribute more than adding
   extra splash screens.
3. **Remove the blank first-login wait.** The session launcher synchronously
   copies the whole offline seed before Hyprland starts; the existing README
   documents about a minute on live media. Prepare installed accounts before
   reboot; reduce live-user copying and expose progress for unavoidable work.
   Share immutable toolchain assets where their update/ownership behavior
   permits it. Preserve per-user writable state and offline functionality.
4. **Implement the three-screen installer and encrypted autologin.** Test
   international keyboards at both password entry and early boot, installer
   failure/retry, screen lock, sudo, and application credential storage.
5. **Improve build feedback and recovery.** Add disk/RAM/CPU preflight and
   Fedora dependency guidance; use unique build IDs; show named phases,
   timings, and actionable failure summaries. Record source revision, local
   modifications, configuration, tool versions, and payload versions.
   Cache signature/checksum-verified downloads independently of disposable
   VMs, and benchmark zstd against the current xz ISO compression before
   choosing a new default. Verify copied output checksums before success.
6. **Automate release qualification and PXE publishing.** Detect Fedora and
   Debian OVMF paths; replace fixed boot delays with bounded readiness checks.
   Exercise live boot → encrypted installation → installed boot → desktop
   parity, with outbound networking disabled. Publish a uniquely named ISO
   and checksum to `/data/pxe/iso` only after verification, then perform the
   required iVentoy refresh/status/list checks. Keep physical GPU and Secure
   Boot coverage as explicit additional tests.
7. **Provide desktop RPM updates.** The image RPM version is currently fixed
   and a signed desktop repository is not yet established. Application updates
   alone cannot deliver the next CybexOS desktop release.

Start with parity and a newly qualified build, then implement the boot/installer
experience. Keep the full offline application image as the primary profile
while measuring size and startup time; a smaller optional development profile
can be considered afterward if the measurements justify another artifact.
